# Windows tracert 出现 Request timed out 怎么办？路由诊断与代理判断

**一句话结论：** `tracert` 中出现 `* * * Request timed out.`，只表示该次路径探测没有在等待时间内收到符合预期的响应，不能单独证明网络中断、某台路由器故障或代理失效；应结合超时出现的位置、后续跳数以及实际应用访问结果共同判断。

## 适用场景

本文适用于 Windows 10、Windows 11 和 Windows Server 环境，主要解决以下问题：

- 在命令提示符中运行 `tracert`，某一跳或连续多跳显示 `* * *`；
- 看到 `Request timed out.`，但网页、远程办公应用或其他服务仍然可以访问；
- 需要判断问题更接近本机网络、家庭路由器、运营商中间路由，还是最终目标；
- 使用代理客户端后，想知道 `tracert` 的结果是否代表浏览器或应用实际经过的代理路径。

Windows 文档说明，`tracert` 会使用逐步增加 TTL 值的 ICMP 探测报文来推断路径。中间设备在 TTL 到期时通常返回 ICMP Time Exceeded 消息，但有些路由器不会返回此类消息，因此该跳可能显示为星号。RFC 792 也定义了 ICMP Time Exceeded 消息及“传输中 TTL 超时”的场景。([Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tracert))

## 分步骤排查

### 第一步：确认命令格式和目标名称

按下 `Win + R`，输入 `cmd`，打开命令提示符。先用一个明确的域名执行：

```bat
tracert /d /w 1000 /h 12 example.com
```

参数含义如下：

- `/d`：不解析中间路由器的主机名，减少 DNS 反向解析对输出速度的影响；
- `/w 1000`：每个探测等待 1000 毫秒；
- `/h 12`：最多观察 12 跳，避免一次命令等待过久；
- `example.com`：替换为你实际无法访问的域名。

Windows 官方文档列出的默认最大跳数是 30，默认等待时间是 4000 毫秒。使用较小的 `/w` 和 `/h` 只是为了快速获得初步结果，不代表网络检测必须使用这些数值。

如果域名提示无法解析，先不要根据 `tracert` 判断线路问题。此时命令还没有进入路径探测阶段，优先检查域名拼写、当前 DNS 解析和本机网络连接。可以先对一个已知可解析的域名测试：

```bat
tracert /d /w 1000 /h 12 www.microsoft.com
```

### 第二步：先看第 1 跳，而不是直接看最后一跳

典型输出可能类似下面这样：

```text
Tracing route to example.com [93.184.216.34]
over a maximum of 12 hops:

  1     2 ms     1 ms     2 ms  192.168.1.1
  2    11 ms    12 ms    10 ms  10.10.0.1
  3     *        *        *     Request timed out.
  4    28 ms    30 ms    29 ms  203.0.113.1
  5    35 ms    34 ms    36 ms  93.184.216.34
```

第 1 跳通常是本地网关或路由器。如果第 1 跳就连续超时，而后续每一跳也没有结果，优先检查以下内容：

1. 当前电脑是否连接到了正确的 Wi-Fi 或网线；
2. 是否刚切换了网络、开启了 VPN、虚拟网卡或安全软件；
3. 默认网关是否可达；
4. 家庭路由器、企业网关或安全设备是否限制了 ICMP 响应。

如果第 1 跳有响应，第 2 跳或第 3 跳开始出现星号，则不能立即判定故障发生在该跳。部分路由器可以继续转发数据包，但不回复路径探测使用的 ICMP 消息。RFC 1812 对路由器处理 TTL 及发送相关 ICMP 消息的行为进行了说明，但实际设备仍可能进行速率限制或直接抑制响应。

### 第三步：判断“中间单跳超时”还是“从此之后全部超时”

这是解读结果时最重要的一步。

#### 情况 A：只有中间某一跳超时，后面又恢复

例如：

```text
  4    24 ms    25 ms    23 ms  198.51.100.1
  5     *        *        *     Request timed out.
  6    42 ms    41 ms    43 ms  198.51.100.8
  7    51 ms    52 ms    50 ms  93.184.216.34
```

这种结果通常说明第 5 跳没有及时返回探测响应，但后续设备和目标仍然可以被探测到。不要把第 5 跳的星号当作确定的故障点，也不要使用该跳显示的延迟直接代表实际业务延迟。

#### 情况 B：从某一跳开始连续超时，但目标最终有响应

例如：

```text
  6    46 ms    45 ms    47 ms  198.51.100.10
  7     *        *        *     Request timed out.
  8     *        *        *     Request timed out.
  9    82 ms    81 ms    83 ms  93.184.216.34
```

这仍然可能只是中间路由器不返回 ICMP，而不是数据包无法继续转发。只要最终目标能够返回结果，就不能仅凭第 7、8 跳的星号认定链路中断。

#### 情况 C：从某一跳开始全部超时，目标也没有响应

这种情况才更值得继续排查，但仍然需要区分：目标主机不响应 ICMP、目标前的防火墙丢弃探测包、路径发生变化，或者本机到目标确实不可达。`tracert` 只观察特定探测报文的响应，不等同于浏览器的 HTTPS 请求，也不能直接替代应用层连接测试。

### 第四步：用 IP 地址重复测试，排除名称解析干扰

先获取域名对应的地址：

```bat
nslookup example.com
```

然后将返回的 IPv4 地址直接交给 `tracert`：

```bat
tracert /d /w 1000 /h 12 93.184.216.34
```

如果域名测试和 IP 测试结果差异很大，可能与 DNS 返回的地址不同、IPv4/IPv6 选择不同或目标使用多个入口有关。此时应记录测试时间、目标域名、解析到的 IP 和完整输出，不要只截取某一行。

如果 `nslookup` 本身无法返回地址，先处理名称解析问题；如果能够返回地址但 `tracert` 仍然超时，则继续观察第 1 跳、后续跳数和实际应用访问情况。

### 第五步：分别测试代理关闭和开启状态

`tracert` 是 Windows 的路径探测命令，官方说明其探测过程基于 ICMP Echo Request、TTL 和 ICMP Time Exceeded 响应。它不是浏览器中的 HTTP 请求，通常也不会像浏览器那样自动读取 HTTP 或 SOCKS 代理设置。因此，开启代理客户端后，`tracert` 显示的路径不一定是浏览器访问同一网站时的实际应用路径。

如果你正在排查边界云加速连接失败，可以按下面顺序操作：

1. 记录客户端未连接时的 `tracert` 结果；
2. 确认订阅已经成功导入，并在客户端连接一个可用配置；
3. 保持客户端连接，再执行同一条 `tracert` 命令；
4. 不要只比较某一跳是否发生变化，而要比较目标是否最终可达；
5. 另外用浏览器或实际业务应用打开目标服务，确认应用层是否恢复。

如果 `tracert` 看起来没有变化，但浏览器访问已经恢复，这并不矛盾：前者观察的是系统发出的路径探测报文，后者可能由支持代理的应用通过另一条应用层连接完成。判断代理是否生效，应优先查看客户端状态、日志和实际应用访问结果，而不是把 `tracert` 输出当成代理链路图。

### 第六步：保存完整输出，便于后续定位

可以将结果保存到桌面文本文件：

```bat
tracert /d /w 1000 /h 20 example.com > "%USERPROFILE%\Desktop\tracert-example.txt"
```

建议同时记录：

- 执行时间，使用具体日期和时区；
- 使用的网络类型，例如家庭 Wi-Fi、手机热点或办公网络；
- 代理客户端是否正在运行；
- 浏览器或应用的实际错误提示；
- 域名解析结果和目标 IP；
- 是只有一个域名异常，还是多个目标都异常。

完整输出比“第 5 跳超时”更有价值，因为路径可能随时间变化，同一设备的不同网络接口也可能产生不同结果。若需要进一步反馈问题，最好同时提供未修改的完整命令输出，但注意删除公网 IP 以外的个人信息、用户名和内部域名。

## 常见问题

### 1. `Request timed out.` 是不是说明节点或服务器挂了？

不一定。它只说明当前探测没有在等待时间内获得符合预期的响应。中间路由器可能限制 ICMP，目标服务器也可能不响应这类探测。应结合后续跳数和实际应用访问结果判断，不能把一行超时直接等同于服务器故障。

### 2. 第一跳显示 `* * *`，但网页还能打开，正常吗？

可能正常。家庭路由器、企业网关或安全设备可以继续转发业务流量，同时不回复路径探测使用的 ICMP 消息。如果网页访问稳定，单独修复第一跳的星号通常没有必要；如果网页也打不开，再检查本机网关、网络切换和防火墙设置。

### 3. 开启代理后，为什么 `tracert` 结果没有经过代理？

因为 `tracert` 发送的是路径探测报文，不是普通浏览器请求，通常不会自动使用 HTTP 或 SOCKS 代理。它的输出不能直接证明浏览器是否使用了代理。验证代理是否生效，应使用支持该代理协议的应用层测试，并结合客户端状态、日志或实际访问结果判断。

### 4. 把 `/w 1000` 改成 `/w 10000`，是不是就能修复超时？

不能。`/w` 只改变每次探测的等待时间，不会让不返回 ICMP 的路由器开始回复。适当增大等待时间有助于观察高延迟网络，但会让命令等待更久，也可能把暂时没有响应的设备误认为只是“稍后返回”。

### 5. 为什么每次运行的路径和延迟都不完全一样？

互联网路径可能存在多条路由，目标也可能使用多个入口地址；此外，`tracert` 的每次探测并不是对网络状态的永久测量。应关注是否能够到达目标、是否存在持续性失败，以及失败是否能在多个时间点重复出现，而不是追求每一毫秒都相同。

### 6. `tracert` 到不了目标，但浏览器却能访问，哪个结果可信？

两者测试对象不同。`tracert` 依赖路径探测报文和中间设备的 ICMP 响应，浏览器通常使用 TCP、TLS 和 HTTP，并可能通过代理、缓存或不同的地址族访问。对于“网页能否打开”这类问题，应用层结果更直接；`tracert` 适合辅助判断路径和响应位置。
